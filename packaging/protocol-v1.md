# Native protocol v1 (not the historical Python wire)

Schema `ao-reason-native/1`. New native state only; no legacy ledger import or mixed-wire interoperability claim.

A JSON object has exactly schema, message_id, deployment, from, to, run_id, attempt, epoch, kind, sent_at, expires_at, payload, mac. Required IDs are nonempty, bounded ASCII identifiers/addresses; attempt is u32 >=1; times are u64 seconds. Allowed kinds: start, cancel, decision, status, approval, report, error, probe, ready. Payload is a JSON object; the whole serialized envelope, including routing, JSON escaping and MAC, must be <=65,536 bytes. Canonical nesting is bounded32. Only integers (i64/u64), no floating-point values in payload. Unknown envelope fields are rejected. An accepted envelope kind is not authorization for every receiver: normal Runner commands accept only start/cancel/decision from Controller A, while readiness has a separate probe/ready path.

MAC: HMAC-SHA256 with exact32-byte trusted node key; hexadecimal lowercase64. Canonical preimage omits mac, lexicographically sorts all object keys recursively, compact comma/colon JSON, Unicode encoded UTF-8 (not ensure_ascii), serde_json JSON escaping including controls, no slash escaping. Arrays retain order. Whitespace in inbound JSON is not signed; parsed canonical values are. Execution traffic selects keys using persisted assignment identity, never untrusted claimed sender alone. Readiness has no task assignment: its configured sender/node key must be followed by current persisted probe correlation as described below. Verification is constant-time via hmac verify_slice.

Time: expiry strictly greater than now; sent_at <= now+45; expiry > sent_at; expiry-sent_at <=300. Deployment and destination must equal trusted local config. Local diagnostic template IDs are sum-native-v1 and control-native-v1. Real-mode trusted configuration permits sum-v1, control-v1 and project-work-v1; these are fixed templates, not model-selected commands. Unsupported kind/schema/ID/shape/time/MAC is rejected before state application. A valid MAC is not permission to release a slot: exact persisted execution + independently sourced exit evidence is still necessary.

## Readiness probe/ready (project-split-ready-v01)

Controller A emits a signed probe only for a configured admitted, non-draining node, addressed to its trusted node ID. The probe has fresh run_id and epoch, attempt=1 and payload {"templates":[...]}. The Controller persists the current per-node probe's run_id, epoch and 60-second response deadline. Ordinary envelope TTL checks still apply independently.

The Runner verifies the probe MAC/deployment/destination, requires from=A, kind=probe, an available configured AO project from its loopback HTTP project lookup, and support for every requested template. It queues a signed ready reply to A with the same run_id/attempt/epoch and payload {"address":"<configured Runner address>","templates":[...],"ao_project_ready":true}. The ordinary probe Envelope TTL is independent of the Controller's 60-second readiness deadline: ready TTL is strictly in (0,60], is capped by both the verified probe sent_at+60 deadline and the probe expires_at, and an expired or overflowing deadline is rejected before outbox insertion.

The Controller checks the configured sender key, destination A, current probe run_id/epoch, attempt=1, unexpired probe deadline, exact configured address and advertised template coverage before setting that in-memory node healthy. This is bounded transport/AO-project capability evidence, not proof of model execution, process exit, durable health/admission reconciliation, artifact quality, Linux readiness or live integration. It does not silently set global GUI real readiness to Ready.

## Structured document start

A project-work-v1 start payload contains template, deadline and project_work. The nested object's schema is project-work/1 (distinct from the template ID), with project_id, action_id, stage, document {version,sha256,text}, tasks, target_task, repair_reason, repair_round, test_spec and artifact. Stages serialize as split/redo/develop/test/repair. Each task carries id/title/description/acceptance/depends_on/review/reason. Frozen test_spec and artifact inputs, when present, carry sha256/text. Original document text is UTF-8 data bound to its exact U version and lowercase SHA256, not an executable command or prompt override. The host owns the stage instructions.

ProjectWork validates bounded input, task identities/dependencies and stage gates. A document import may contain up to 256 KiB, but that does not guarantee it can execute: before inserting a project run, Controller constructs, signs and verifies the actual serialized start frame for every configured project-capable route. Frames exceeding 65,536 bytes are rejected before queue insertion; the imported document remains. Runner persists the accepted structured input and requires identical content on a repeated start for the same execution. These wire/stage definitions do not assert that every stage is implemented end-to-end.

## Trusted result workspace and pending exit

Config ao-reason-config/1 has optional workspace_root (default None), supplied by trusted host configuration, not the document, task data or envelope. Runner resolves it relative to the host config directory; the AO adapter canonicalizes an existing directory. This path is not a new envelope field.

For document results, the adapter requires workspace_root, asks AO for the exact session workspace, canonicalizes that workspace and requires it to be a strict descendant of the configured root. It reads a regular, non-symlink project-result.json capped at 48 KiB. The project-result/1 record must match project_id/action_id/stage/document_version/document_sha256 of the accepted work. Split/redo task arrays are validated for bounded content, unique IDs and acyclic dependencies; returned tasks are not automatically user-approved.

A validated result is reported as stage_result_validated=true, passed=null, state=report_pending_exit. It is not independent process-exit or product-test evidence: reservations remain and Start/development cannot be inferred as available. In project-review-ready-v01, explicit task approval/rejection is allowed while the only unresolved action is the split report_pending_exit. The initial result digest, full task/dependency input and pending review state commit atomically; repeat observation must match that digest and must not reset approved/rejected decisions or their reasons. Even all-approved tasks do not unlock Start until credible exit is established. These are source-level stage gates whose matched GUI/runtime validation must be reported separately; no live AO/Reason/model, Linux or native GUI acceptance claim follows from owned fixture tests.

Independent golden vector uses a literal fixture and Python3 standard-library json.dumps(sort_keys=True,separators=(',',':'),ensure_ascii=False) and hmac SHA256, not the Rust helper under test. Its exact preimage and expected digest are asserted in Rust tests. This does not prove arbitrary upstream protocol compatibility.
