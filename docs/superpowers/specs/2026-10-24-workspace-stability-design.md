## 1. 用户目标与已确认范围

用户要求“更方便、更易用，稳定必须放第一位”。具体反馈和澄清：

- 当前使用 `http://127.0.0.1:58593/`。
- 找不到历史项目入口，不是已经确认项目数据丢失。
- 操作后不知道何时完成，不清楚是否还在运行；这是当前“不稳定”的主要具体表现。
- 历史项目仅限当前工作台创建的项目。不汇总其他 ZIP、解压目录或 userdata，不迁移项目。
- 保留此前交付验证目标：更新版本上的真实模型完整闭环、干净 Windows 首次使用、最终人工验收。
- 新增用户要求：Linux x86/ARM 正常稳定运行；使用场景为无桌面的服务器，发行版为基础 Ubuntu。
- 本方案选择 Ubuntu Server 24.04 LTS，x86_64（amd64）和 ARM64（aarch64）为首批 Linux 基线；用户没有指定版本或位宽，这是为减少兼容面作出的建议，不是用户已确认的版本承诺。32 位 i386/ARMv7、其他发行版暂不纳入。
- 无桌面服务器采用单用户、同一操作系统账号运行和管理，建议通过 SSH 本地转发访问。公网开放、多用户平台和反向代理不是本轮默认范围。

下面未由用户指定的界面和实现选择均为本方案建议，不当作用户已经同意。

## 2. 现场代码依据和不能混淆的结论

已检查 `live.js`、`setup.js`、`live-output.js`、`index.html`、`styles.css`、`p1/server.py`、`p1/state.py` 和现有 HTTP/状态机回归。

已存在的行为：

1. 历史项目只有普通下拉框，文案为“受管理项目”；没有明显的历史项目列表或搜索。侧栏、面包屑、标题仍含静态演示项目内容，容易误认当前项目。
2. `report()` 将操作错误写入连接提示；下一次成功轮询会将其覆盖，错误不能稳定保留。
3. `api()` 没有统一的请求超时；`refresh()` 先读项目再等待 setup 读取，后者悬挂时整个项目刷新不落地。
4. 已有 revision 合并和后台 commandId 去重，但没有面向浏览器的命令回执查询。POST 响应丢失时，页面不能明确区分“未提交”和“已提交但未收到响应”。新建项目当前没有幂等请求标识。
5. 需求输入仅在聚焦时不被 render 覆盖，切换、失焦、刷新缺少清晰的未保存草稿处理。
6. 执行计时、宿主校验和可信复跑信息已经存在，但主要放在日志区域；阶段主说明多数是通用提示，没有贯穿所有操作的结果和下一步。

以上说明实际的可用性缺陷和需要回归验证的稳定性风险。尚未证明后台随机丢数据、现有项目损坏或历史按钮问题只有一种原因，不据此承诺这些故障已复现。

## 3. 优先级和不变条件

顺序：数据与执行安全 > 操作状态可信 > 项目找回 > 布局美化。

- 沿用原生 JS/CSS、Python loopback HTTP、SQLite 和三岗位执行，不迁移框架；保留 Windows 启动器，新增 Linux 启动入口及平台适配。Linux 必需的系统库、systemd/cgroup 能力和对应架构运行时须明确列出，不谎称零依赖，不静默安装。
- 不更改现有任务批准、CAS、独占租约、Job Object、证据冻结、可信复跑、会话、条款门禁。
- 不把 HTTP 请求成功、CLI exit 0 或日志结束等同于模型阶段完成、测试通过或人工验收。
- 不自动重发任何改变状态的请求，不自动付费重试，不恢复执行被服务重启中断的任务。
- 不删除锁、编辑 DB 状态、复制同意记录或伪造证据以消除报错。
- 不重启用户现有服务，不改其项目；研发和故障注入均用隔离数据。
- 不修改历史静态演示的原始 HTML/JS；新增样式限定真实模式，动态覆盖真实模式的错误演示文案。
- 不提交、推送或创建 worktree。旧 ZIP 不覆盖。

## 4. 用户界面

### 4.1 始终能找到“我的项目”

页面顶部提供明确的“我的项目”入口和当前项目名；桌面与移动都能使用，不能仅依赖会在手机隐藏的侧栏。

- 展示当前工作台的完整项目列表，支持名称搜索。
- 每项展示名称、当前阶段、短 ID；有事件时间则展示最近活动，无可靠时间就写“暂无活动记录”，不编造时间。
- 同名项目用短 ID 区分；列表为空、搜索无匹配、断线保留的旧列表分别显示。
- 点击项目查看原有需求、设计、任务、执行状态和产物，不创建新运行。
- 当前项目和搜索条件在同一页轮询中不跳动，列表不每 1.2 秒销毁重建；兼顾键盘操作。
- 切换后标题、面包屑、侧栏摘要、操作状态和产物预览必须属于同一项目；清除上一项目 iframe。
- 搜索不改变当前项目，不因为当前项被过滤而自动切换。
- 只保存本机页面选择，不向浏览器开放任意文件路径。

### 4.2 首屏可见的“当前进展”

当前项目标题下直接展示状态，不要求用户翻到页面底部或切换技术日志：

- 当前在做什么：排队、生成设计、拆分、开发任务 X/Y、独立测试、可信复跑、等待人工处理。
- 当前动作是否已被后台接受；发出请求不表示接受。
- 有可靠起点才显示已用时间，没有可靠数据时明确说明。不显示伪造百分比或预计完成倒计时。
- 后台确认后才显示完成；例如“设计已生成，下一步下载检查后上传”“任务已拆分，下一步逐项审核”“实际测试和可信复跑通过，等待你查看产物并验收”。
- 失败显示具体原因和安全的下一步；没有新日志不被描述为失败或“模型正在思考”。
- 显示上次成功同步时间；超时或断线时标记当前内容为最后已知状态，不能继续冒充实时状态。
- 明确区分“本次点击已完成”和“整个项目已完成”。开发者任务完成、测试员完成及可信复跑之间不出现提前的“项目成功”。

阶段信息优先来自 `/api/state`；遥测只补充当前绑定 attempt 的细阶段和计时，不能覆写权威阶段。遥测不可用时保留权威阶段，不因此宣告任务结束。

### 4.3 稳定保留每次操作结果

- 保存、新建、上传、审核、生成、拆分、开始、暂停、终止、下载等操作都有明确的处理中和结果。
- 成功提示包含所作用的项目；失败提示不被后台轮询覆盖。新动作或用户明确关闭才替换该提示。
- 结果按项目隔离；切换到其他项目不展示上一个项目的成功/错误提示。
- 对异步模型动作，先显示“后台已接收，排队/执行中”，阶段结束后显示权威结果。
- 设计下载只表述“文件已准备并交给浏览器下载”，不能声称文件已经保存到用户磁盘。
- 按钮暂时不可用时说明原因，不让用户靠反复点猜测。
- 不增加浏览器系统通知、弹窗轰炸或外部服务。

## 5. 稳定性实现边界

### 5.1 请求超时、轮询与版本隔离

- 给状态、setup、遥测和普通 POST 设置独立有界超时；setup recheck 使用更长边界，因为实际固定探测和依赖检查允许几十秒。具体秒数由实现根据现有服务上限决定并写入测试。
- 状态同步与 setup 读取分离，不让 setup 悬挂阻塞项目列表和阶段更新；setup 过期/失败时单独禁用需要接入就绪的操作。
- 每类读取最多一个在途请求，完成后调度下一次；失败采用有上限退避。允许自动重试只读请求，禁止自动 POST。
- 响应必须通过项目、revision、选择代次以及相关 attempt/epoch 检查后才更新当前视图；新建项目之后到达的不完整旧列表不能将新项目抹去。
- 403 会话失效与短暂网络错误分开显示；会话失效提示通过原启动器重开认证页面，不无限高速轮询，也不放宽认证。
- POST 的前端超时不取消后台任务；必须显示“结果尚未确认”，不能显示“已终止”或立刻解锁重复付费操作。
- 刷新和换页不发送模型动作，断线恢复只读同步后台，不重新开工。

### 5.2 命令回执与不确定提交

沿用已有 `commands` 中的幂等记录，并新增受当前会话保护的只读回执接口。接口按项目和 commandId 查询，返回已记录动作的必要标识、提交 revision，以及是否找到回执；再读当前 state 获取最新阶段，不将旧回执当作当前完整状态。

- POST 发出前记录最小操作描述：projectId、commandId、kind、expectedRevision、时间；不持久化原始需求/上传正文，不新增保存 bearer 的地方。
- 在同一浏览器标签的 sessionStorage 中保存最小描述，以便刷新后能只读核实；存储不可用时退回内存并明确不能跨刷新恢复，不让页面崩溃。
- 超时、断线或响应解析失败后，保留“结果待确认”，自动只读查询回执和项目状态，不发出重试 POST。
- 回执已存在说明该操作被后台接受；之后的成功/失败依据当前 attempt 和权威状态。
- 暂无回执不等于“未执行”，尤其请求可能仍在等待 action_lock。此时不允许重复写入同一项目；保留刷新确认/会话恢复说明。不能通过生成一个新 commandId 绕过不确定结果。
- 已确定的 4xx 拒绝、版本冲突与传输未知结果分开处理；版本冲突保留本地草稿，不自动重放用户修改。
- 恢复描述只用于读取，不带来的旧操作自动执行，也不因此自动同意条款或最终验收。

为新建项目增加向后兼容的可选幂等标识：现有 `{name}` 调用仍可用，新 UI 使用固定 commandId。标识、名称指纹、创建的项目 ID 必须在同一事务中记录；同 ID 同内容只返回同一项目，同 ID 不同内容拒绝。使用新增的本机回执表（`CREATE TABLE IF NOT EXISTS`），不重写旧项目状态。旧客户端不声称具备此增强去重能力。具体表名及接口 URL 留给实现，但必须有真实服务回归。

本轮不新增自动重试/强制解除未知提交的捷径；若回执长时间查不到，显示可操作的诊断信息和明确阻塞，不为“看起来恢复”而冒重复执行风险。

### 5.3 草稿与项目切换

- 需求草稿按项目隔离，显示“未保存”；失焦、轮询或切换不能无声覆盖。
- 同一标签切换回来可以继续草稿，刷新前有未保存提示。只将草稿保留在内存，本轮不在浏览器额外持久化需求正文；刷新确实放弃时明确告知。
- 远端 revision 更新不能覆盖正在编辑/未保存的草稿；显示版本变化，保存按 CAS 拒绝而不是自动合并或覆盖远端。
- 请求、上传读取过程中禁止切换，防止上传/保存被应用到另一个项目；异步返回仍显式检查项目绑定。
- 自动保存不在范围内，避免无意使设计/批准失效。用户明确点击保存才改变后台需求。
- 未保存需求触发生成时，先确认保存成功且仍是同项目同内容，再提交生成；保存失败不能接着付费生成。

## 7. 测试和验收标准

先写能在现有实现失败的回归，再作最小改动；用隔离的真实 HTTP/Chromium，不把 fixture 状态当模型成功。

必须覆盖：

4. 排队/运行/宿主校验/可信复跑/待人工处理/blocked 的主状态可见；缺少遥测不伪造完成。
5. 慢 setup 不阻断项目状态更新；状态或遥测请求悬挂到有界超时后能恢复读取且无重叠洪泛。
6. POST 在后台已提交但响应丢失、仍在等待处理、明确被拒绝等场景逐一验证；刷新后只查询回执，不能新增 attempt、command 或项目。
7. 双击/连点生成、保存、审核、新建与相同 ID 回放，不产生重复模型 attempt/项目；跨标签 CAS 冲突保留草稿。
8. 旧 poll 晚于保存/新建、项目快速切换、旧 attempt 遥测迟到，不回滚新状态、不污染其他项目。
9. 未保存需求失焦/切换/远端更新时不丢，明确保存失败后不触发生成。
10. 新表添加不改变旧项目和证据字节/状态；旧格式新建调用兼容；回执接口认证、Origin、项目范围及非敏感返回符合现有规则。
11. 包内完整性清单、依赖路径及现有全部套件不回归。原静态演示原字节不动。

测试需报告每条实际结果、失败和跳过项；不以计数替代用户流程。增加有界的多项目/刷新/断线循环稳定性检查，但循环通过不构成“绝无故障”的承诺。

## 10. Ubuntu 无桌面服务器：新增平台范围

### 10.1 支持矩阵和现场依据

首批拟支持三个独立目标：

| 平台 | 架构 | 交付与验证边界 |
| --- | --- | --- |
| Windows | x86_64 | 保留现有 CMD/Job Objects 适配和全部现有验证；当前运行实例不动 |
| Ubuntu Server 24.04 LTS | x86_64 / amd64 | 原生 Linux 运行时、无 DISPLAY 的浏览器检查、SSH 远程访问，单独包与报告 |
| Ubuntu Server 24.04 LTS | ARM64 / aarch64 | 原生 ARM64 运行时与浏览器，不用 x86 模拟冒充原生通过；单独包与报告 |

已读代码能证明的移植障碍：

- `p1/server.py` 无条件导入 `msvcrt`，根锁是 Windows 字节锁。
- `p1/winjob.py` 的 `JobProcess` 在非 Windows 明确拒绝；`runtime.py`、`reason_mcp.py`、`checks.py`、`environment.py` 直接依赖它。
- `p1/instance.py` 使用 WinDLL、SID 和命名管道；`bootstrap.py` 默认无窗口/UI行为和失败提示也有 Windows 假设。
- `environment.py` 只接受 `win32-x64` 清单、MZ/`.exe`，开发路径和健康检测包含 Windows 专用内容。
- `browser_setup.py` 固定 Windows 浏览器 URL 和 `chrome.exe`；`tools/build_portable.py` 只接受 Windows 清单，复制时也未实现 Linux 可执行权限保留策略。
- 当前已锁定 Playwright 1.58.2 的本地 `hostPlatform.js` 明确识别 Ubuntu 24.04 x64/arm64；其 `registry/index.js` 给 x64 的 Chromium 使用 Chrome for Testing `chrome-linux64/chrome`，给 arm64 使用单独 Chromium 构建 `chrome-linux/chrome`。这是包内代码依据，不证明任何 Linux 下载已完成或浏览器已能启动。
- 在线官方文档和 reason-network v0.10.8 release API 本轮未能访问；`gh` 未安装。reason 的 Linux 两种架构资产是否齐全、精确 SHA256 和版本行为尚未核实，不能猜下载 URL、借用 Windows 哈希或更换版本后不报告。
- 本机只读检查：`wsl.exe --list --quiet` exit 1，无可用发行版结果；docker/podman 不存在。当前没有已确认可执行本项目的 Linux 环境，更无原生 ARM64 实测证据。本轮不安装、启用或连接未知服务器。

### 10.2 平台边界，保留同一业务状态机

只抽取确有差异的四类平台能力：运行时/架构解析、独占根锁、同用户实例通道、受控进程生命周期。项目、CAS、批准、命令回执、证据与界面保持同一实现，不复制成两套工作流，不为了移植重写业务。

- Windows 继续使用现有已验证的 Job Objects、SID 及命名管道。Windows 专有模块按平台加载，Linux 导入核心服务不得先触发 WinDLL、msvcrt 或 `_winapi`。
- Linux 根锁采用本机文件系统上的内核非阻塞独占锁，在任何 SQLite 恢复前取得；锁持有到旧进程清理完成之后。不支持 NFS/SMB 共用 userdata，不按锁文件存在与否判断所有权，不删除锁来抢占。
- Linux 实例通道用当前 UID 专属 Unix domain socket，权限目录 0700、socket 0600，检验 `SO_PEERCRED`。处理 socket 路径长度、同 UID 重开、不同 UID 拒绝及根锁仍被持有的情况，不把 HTTP 裸地址当同用户控制证明。
- 运行账号为普通非 root 用户；项目数据、SQLite、reason home、MCP配置和私有接入材料限该用户。默认不提权、不改全局 PATH/认证、不注册系统自启、不混用不同 Linux 用户的 Claude 配置。

### 10.3 Linux 子进程所有权是稳定性硬门槛

不能用 `Popen.terminate()` 或只确认父 PID 退出，替代现有 `treeStopped` 语义；单纯进程组也不能涵盖会 `setsid` 的后代。

本方案的技术选择：Ubuntu 以 systemd 用户服务配合 cgroup v2 管理工作台及每次受控执行，所有权和启动次序须在计划中落实：

- 启动前检查当前用户 systemd manager、统一 cgroup v2、可验证的 unit/cgroup 控制能力和需要的工具；缺少能力明确阻塞真实执行，不静默退回弱进程组策略。
- 子命令在受控 unit/cgroup 内才允许执行，从第一条可执行用户命令开始就受管理。具体 wrapper/握手方式由计划确定并先通过真实非模型回归，不能有先启动、后归属的逃逸窗口。
- 每个 owned unit 使用完整控制组清理语义和有界 TERM→KILL；普通退出、父先退出、双重 fork/setsid、超时、输出超限、用户停止、CLI 异常、启动失败都须检查 cgroup 已空并回收管道/观察线程，才能返回 `treeStopped=true`。
- 工作台宿主自身也由受控用户服务运行，SSH 断开不让宿主半退出、模型失管。宿主意外被杀时，每次执行的 unit 必须与宿主生命周期绑定，避免 sibling unit 继续运行；恢复时先核对、停止并验证本工作台旧 unit，完成后才允许新的写租约。PID 文件或 `kill(pid,0)` 单独不足以提供证明。
- 不能确认某旧执行或持有租约是否停止时保留 `blocked/leaseUnknown`，不把已有 Store 恢复保护自动解锁，更不自动续跑/重试付费步骤。后续安全解锁只可基于可核验的旧执行绑定和全组停止证明，不提供跳过按钮。
- 不默认启用 user lingering 或开机自启。当前 SSH 会话/用户 manager 不满足持续运行前提时须在启动前说明并阻塞承诺的后台模式，由部署者显式决定配置；不得为了后台运行自行执行 sudo、loginctl 或安装服务。
- cgroup、MCP白名单和文件路径校验是生命周期/能力控制，不被描述为完整 OS 安全沙箱；同 UID 恶意程序和 root 超出本轮保证。

### 10.4 无桌面访问必须同时涵盖控制页和产物预览

默认不监听 0.0.0.0，不新增公网账号系统，不放宽 CORS/Host/Origin/CSP；只支持 SSH 本地转发。

- 固定并显式配置互不相同的控制端口和预览端口；Linux 默认建议 8787/8788，仅绑定服务器的 127.0.0.1。端口占用明确失败，不偷偷挑新端口导致 SSH 配置失效。
- 客户端将两个端口分别以 `127.0.0.1:同端口` 转发至服务器 `127.0.0.1:同端口`，保留当前严格 origin 和分源预览隔离。只转发控制端口的方案不合格，因为 iframe 会指向访问者本机另一端口。
- 接入说明给出两个 `-L`、`ExitOnForwardFailure`、保持连接/断线重连步骤；客户端端口冲突时显式选择另一对并同步配置服务器，不使用 URL 参数任意改目标、不放宽 origin 来绕过。
- Linux 不调用 `webbrowser.open()`，也不要求桌面/Xvfb来运行产品检查。访问者自己的浏览器通过隧道打开页面；headless Chromium 在服务器执行独立测试。
- 一次性 bootstrap 只在用户显式索取时签发，维持短有效期、单次交换、不进普通日志/命令行参数/共享状态文件。初次建立隧道后再索取，避免安装、转发准备期间早已过期。
- 同 UID 的接入命令经私有实例通道向运行中的工作台请求新链接，并通过受保护、短期的本机交付文件提供；文件及父目录权限分别 0600/0700，拒绝符号链接，过期清理。终端默认只显示非敏感地址和私有文件位置，不将 capability 交给 systemd journal。重复索取不重启宿主或模型；人工将链接用于其本机浏览器不被当公开发布授权。
- SSH断开时界面显示离线和最后已知状态；重新建隧道只读恢复，不新建项目、不重发模型命令。会话过期通过上述本机命令重新签发，而非禁用认证。
- 单用户 loopback 服务不是多租户防线，服务器须为用户信任的单用户运行环境；不默认为公共共享主机安全方案。

### 10.5 Linux 依赖、下载和交付

- 新增两个分别标明 `linux-x64` / `linux-arm64` 的版本化安装包（优先 tar.gz 保留执行位），附 `start-workbench.sh`、接入/停止/诊断说明、依赖清单、许可证和 SHA256，不覆盖现有 Windows ZIP。
- Ubuntu 使用系统 Python 3.12 及标准库，启动前实际检查 sqlite3、ssl、平台能力；Python 不在 Linux 包中强行复制 Windows 嵌入版。随包固定原生架构 Node、Playwright/core 和 reason；不增加 Python 第三方库。Node/reason 的精确版本及归档哈希在构建前核实，缺一项该架构不可发布。
- 构建器按实际 OS/CPU 匹配清单，错误架构明确失败，不调用 Rosetta/QEMU/Wine冒充兼容，不带开发机绝对路径回退。提取拒绝越界、链接和不安全模式，保留已允许普通文件的执行位并禁止 setuid/setgid；需要链接的官方包采用经过审查的重排策略，不直接放宽解压限制。
- Linux Claude 原生程序由使用者按该架构官方步骤安装和配置，工作台不随包提供或读取密钥。发现路径须按 ELF、实际架构和执行权限验证，固定无模型探测及登录未知门禁不变。官方安装/架构支持尚需核实，不能猜原生路径或自动联网安装。
- reason-network 两架构资产缺失时不替换成假的 TASK/ACK/RESULT或内存总线。可评估相同固定源码的可复现构建，列明工具链、来源和哈希；若不可行，报告该架构阻塞，不声称完成支持。
- 浏览器按 Playwright 固定版本与架构分别锁定真实官方归档、执行路径、文件清单、哈希、许可证/条件；ARM64不是把 CFT 的 linux64 路径改名。不得复用 Windows 浏览器同意回执，条款不同需使用者另行确认。
- 无 DISPLAY 模式真实启动浏览器、完成声明式断言并独立可信复跑，不能只跑 `--version` 或 import。生产测试浏览器启用 Chromium sandbox（Playwright 默认配置不能被想当然视为已启用）；普通用户权限、userns/AppArmor 及缺失动态库都要检查。不能以 root、`--no-sandbox`、disable host validation、关闭TLS或更换不受信镜像作为默认修复。
- Ubuntu 最小安装缺的系统库用版本化手册列出准确包名和经过审核的安装命令，由用户/管理员显式执行；工作台本身不自动 apt、sudo 或改 sysctl/AppArmor。系统库及systemd前提未满足时提供具体诊断，禁止误报就绪。
- 所有运行数据以显式数据根目录为准，包括浏览器/条款回执和下载内容，不像当前源码把某些 setup 数据隐式固定到 BASE/userdata。Windows 默认仍保持原目录布局；Linux包目录和数据根都需当前用户可写，升级须正常停稳后备份/切换，不交叉复用正在运行的 Windows userdata。
- 本次只有 Windows 隔离副本的真实条款/浏览器授权。Linux 新依赖条款与首次下载不是已经获得的同意；网络下载和所需系统变更各自保留许可边界。

### 10.6 Linux 专项验收与未具备环境时的处理

两架构分别记录 OS/CPU、Python/Node/reason/Claude/Playwright/浏览器版本、哈希、原生或模拟、systemd/cgroup 条件及每项结果：

1. 全新基础 Ubuntu 24.04 安装，普通用户、无桌面、无 DISPLAY，按发布文档安装明确列出的系统依赖。自动静态检查不能替代这一项。
2. shell入口、同根并发启动唯一owner、同 UID 重开、错误 UID 拒绝、权限/执行位/错误架构、socket路径过长、端口冲突、不可写/磁盘不足等实测。
3. 经真实 SSH 隧道访问控制页和分源预览，旧链接不可重放、裸地址仍被门禁、令牌不落journal/普通日志；只读断线/重连和会话恢复不造成新项目/命令/attempt。
4. 全部平台无关状态/回执/HTTP/浏览器回归，以及各平台专有生命周期测试。Windows测试不能整体skip后称Linux全套通过，反之亦然；OS专用跳过逐项解释。
5. 使用真实非模型子程序覆盖普通及父先退出、后代 setsid、忽略TERM、输出超限、超时、用户停止、宿主SIGTERM/SIGKILL与恢复；断言cgroup空、无残留写者/浏览器/reason daemon，旧运行不自动恢复。无法确认就继续阻塞。
6. 原生架构 headless Chromium 在有sandbox且无DISPLAY条件下完成真实声明式产品检查、冻结测试和独立可信复跑，并产出不可伪造的现有证据链。模型边界替身结果明确标为免费测试。
7. 有界多项目/刷新/断线/进程退出循环，检查无重复写入、跨项目串内容、句柄/进程堆积、文件权限倒退；不由有限循环承诺“绝无故障”。
8. 各自最终 tar.gz 独立解压、重新散列、权限核验、从最终包启动和运行前述流程；两架构分别出报告。QEMU容器/WSL可补充验证但不能冒充干净原生Ubuntu服务器/原生ARM64结果，普通容器也不能替代宿主systemd/cgroup生命周期验证。

没有可用环境时，继续做可完成的源码与免费 Windows 回归，但 Linux 行标记“未验证/阻塞”，说明需要可授权的全新 Ubuntu x86_64 与原生 ARM64 主机（或对应原生架构虚拟机），不擅自租云、安装虚拟化或使用记忆中的业务服务器。

当前“一次新真实模型闭环”授权总数不因新增两平台变成三次。两 Linux 架构的真实模型闭环若要另外执行，需要另行明确费用授权；Windows那次完整闭环不能作为Linux模型可达/执行已验证的证据。最终报告分别呈现免费平台流程、真实模型流程、干净环境、人工验收四个状态。
